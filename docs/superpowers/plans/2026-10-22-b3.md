# B3 模拟支付、关闭屏障与库存确认

**Spec:** 资料包主文档7.2/7.3及03规范第5节、实施批次B3。用户要求开始下一项，先完成B2收尾，再实施B3。沿用不测试、不SSH、不提交Git。

**Architecture:** payment和simulator各自真实逻辑库。公共金额/身份来自订单payment-intent，只允许待支付且未超期提交；稳定paymentNo唯一意图同时作为pay/close屏障。模拟通道在同一记录上串行pay/close/异步成功，CLOSED墓碑拒绝迟到pay。支付的本地结果应用统一用于响应、回调和查询，资金流水、退款额度、结果通知Outbox同事务。B3通过持久HTTP通知交付Outbox，RabbitMQ发布在B5替换，不声称MQ已实现。

**Contracts:** `PaymentContracts.java`固定DTO；所有HTTP响应ApiResponse包裹。内部独立凭据：payment→user/order使用PAYMENT_SERVICE_TOKEN；order→payment使用ORDER_SERVICE_TOKEN；payment→simulator使用CHANNEL_SERVICE_TOKEN；回调HMAC独立CALLBACK_SECRET；模拟器管理使用SIMULATOR_ADMIN_TOKEN且仅dev。全部随机受保护.local注入，不写仓库。

## Task A 独立模拟通道（委派，只改payment-simulator模块）

- 初次V1按channel_transaction/fault_scenario/callback_task/process_task/audit_log等本批表拆分，完整基线归档docs/database-target；每字段COMMENT。
- POST /channel/v1/payments、POST /channel/v1/payments/{paymentNo}/close、GET /channel/v1/payments/{paymentNo}；X-Caller-Service=payment、X-Service-Token=CHANNEL_SERVICE_TOKEN。
- ChannelCommand/ChannelFact绑定orderNo、paymentNo、金额与CNY。没有记录时close也按命令建立CLOSED墓碑；状态终态不可反转，异步推进也串行同一记录。
- dev场景POST /simulator-admin/v1/scenarios，Header X-Simulator-Admin-Token，支持SUCCESS/REJECT/PROCESSING/RESPONSE_TIMEOUT/CALLBACK_LOST/CALLBACK_DUPLICATE，按paymentNo一次绑定，不依靠随机全局开关。超时模式先提交事实再返回504；PROCESSING持久任务稍后成功，关闭可胜出。
- 回调目标固定配置payment服务/callbacks/v1/payments；Callback DTO的UTF8原始JSON体，头X-Notification-Timestamp(秒)、Nonce、Signature，HMAC-SHA256(timestamp+换行+nonce+换行+rawBody)，常量时间比较。callback_task领取/重试/租约版本；重复回调同notificationNo，重试可换时间戳/nonce，body不可变。
- 配置common+dev/test/prod一个YAML，dev真实13316数据源、Flyway业务进程关闭；DatabaseMigration独立入口；不改根启动脚本。输出需要的表权限与环境变量。不运行测试或业务请求、不连接远程。

## Task B 支付服务（委派，只改payment模块）

- 注册POST /api/v1/payments（body orderNo，Idempotency-Key必填）与GET /api/v1/payments/{paymentNo}，用户JWT验签+用户服务最新版本+本人订单归属。金额/支付号取GET order/internal/v1/orders/{orderNo}/payment-intent，用PAYMENT_SERVICE_TOKEN。
- internal POST /internal/v1/payments/{paymentNo}/close（CloseCommand），GET同号、POST同号/query-channel，order凭据；close即使支付单未存在也查订单权威数据创建close_intent=YES意图。公共submit与close锁同payment_order，不能出现本地关闭后又提交新支付。
- 通道事务外HTTP调用，CHANNEL_SERVICE_TOKEN；固定URL及1s/3s超时，禁止隐式写重试。稳定支付号持久任务Submit/Query/Close（数据库租约claim_version，未知先查原号，查无记录仅在没有close_intent时重放pay；close必须真正调用通道关闭，不能仅查无记录即CLOSED）。
- 响应/查询/签名回调统一应用ChannelFact，校验绑定/金额/CNY/版本/终态。成功只写一次PAYMENT_SUCCEEDED流水，初始化refund_account；同事务生成Outbox Event。关闭意图不能抹掉真实成功。矛盾升级人工，不能覆盖终态。
- HMAC回调验真在去重前；原始body<=64KB，5分钟窗口，Callback DTO。channel_notification存同notificationNo摘要，合法重复返回ack=true，异参409；未验真不占号。
- Outbox通过HTTP POST order/internal/v1/orders/{orderNo}/payment-results，Event DTO，payment凭据；持久租约/重试，ACK后置SENT。只对SUCCEEDED/FAILED/CLOSED发通知。
- 支付数据源、JWT、service URL、秘密配置；独立DatabaseMigration；实际流水分页可做平台GET /api/v1/admin/payment-ledger。保留未实现退款接口拒绝，不伪造退款。输出表权限。不得修改公共DTO/根脚本或order模块。

## Task C 订单/库存/启动集成（root）

- payment-intent内部只读权威数据；payment-results原支付号事实幂等应用。订单PENDING_PAYMENT与CLOSING原子竞争：成功胜出PAID+COMMIT任务，关闭胜出坚持取消。
- 商品confirm内部实现COMMIT，将reserved扣除而非回可用，重复不重复流水，RELEASE墓碑拒绝确认。
- 扩展原订单持久流程任务承担后续库存确认/关闭，受控重启已成功任务必须增加claim_version并审计，同一锁顺序task→intent→order。PAID确认后stock_sync_status=CONFIRMED；当前无发货接口，不能伪造履约完成。
- 待支付取消/到期写CLOSING+RELEASE，但只有通道CLOSED/FAILED才释放；通道SUCCEEDED而关闭已赢，标记LATE_PAYMENT_REFUND_REQUIRED并进入人工，留待B4退款流程，绝不假装退款成功或自动关单。
- 新本机payment/simulator逻辑库、独立账号和迁移、必要网关路由、所有契约/文档。B2及B3实际构建/迁移/启动分别记录。
