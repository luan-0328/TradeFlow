# U1–U4 业务升级实施计划

> 执行方式：按模块分工开发，主执行者逐步集成；用户明确要求全部开发完成后一并测试，不部署。

**Goal:** 在现有交易正确性基础上补齐日常使用、多商户经营、跨商家交易及模拟结算治理。

**Architecture:** 保留服务数据库边界；多商户通过最新成员关系、资源归属、经营状态与商家选择共同授权；交易组原子创建本库子单意图，子单沿原 Saga 独立支付恢复。结算使用独立库与不可变账本，跨服务查询全部在事务外。

**Tech Stack:** 现有 Java21、Spring、MyBatis/XML、MySQL、Vue、RabbitMQ、Nacos。

**Spec:** [升级路线](../../upgrade-roadmap.md)。本计划覆盖 U1–U4，不含 U0 交付门禁和 U5 部署。

## 执行约束与决策

- 不执行开发中测试；先写测试源码，最后统一运行。编译和类型检查也安排集成后，避免并发覆盖 target。
- 不 SSH、不部署、不升级现有业务数据库、不重启既有服务、不提交推送。
- 迁移追加 user V6 / product V6 / order V8 / aftersale V5；结算独立 V1。以实际现有最高版本复核。
- 保留旧 record 构造器兼容；新字段使用重载构造器或独立扩展 API。
- 默认逻辑仓库仍 warehouse_main；SKU 全局唯一，商家隔离沿商品归属强制校验，不宣称多仓。
- 交易组最多 10 个商家、每单最多 20 个 SKU；组内商家去重，各子单独立付款。
- 结算服务费默认 0bps、冻结期默认 7天，可配置且按交易冻结快照；模拟完成不等于真实出款。
- 第一套运费按商家固定费配置；必须进入购买件实付分摊及退款授权，不单独增加无法退款的金额。
- 商家优惠券为路线后续可选范围，本次不加入平台券或真实渠道。

## 审查重点

1. 商家选择头不是权限，列表/详情/写入/恢复/文件均需校验所选商家与最新成员关系。
2. 商家停用阻止新经营，但历史退款恢复不能因经营停用丢失义务。
3. 交易组同键异参、部分创建和迟到响应保持原号；不能把受理当作付款成功。
4. 运费分摊前后逐分守恒，原商品单价保留，购买件实付是退款权威。
5. 结算与退款交错必须冲正，重复/乱序事实不能重复记账或静默漏账。
