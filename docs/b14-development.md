## 已修正的问题

| 问题及代码证据 | 修正 |
| --- | --- |
| MessageOperations.list给deferred/failure同时返回event_id与记录主键；后台原id()先取event_id，而retry接口按deferred_id/failure_id查找 | 严格按消息类别选主键，缺失主键时拒绝提交，不回退另一个编号 |
| useCommand.reset需要等待Web Lock；六个管理页面在等待前检查弹窗代际，等待后未复查，关闭/切资源后仍可能继续改页面 | reset后再次检查generation，对账列表刷新后再次检查，防止旧结果重新打开详情 |
| 商家售后上传捕获generation，但选择另一个审核动作未递增它，旧上传响应仍可能加入新动作证据 | 切换处理动作递增generation，清空证据与上传状态，旧响应不写回 |
| 售后预览只对成功分支比较版本，旧请求catch/finally仍可覆盖新错误/加载状态 | 成功、失败、结束均核对同一version；输入变化作废预览并取消旧请求、复位对应忙状态 |
| 购物袋owner和深度持久化watch都按默认批处理执行，同事件中先修改购物袋再切换账号存在归属时序窗口 | 账号切换同步设owner并替换购物袋，持久化同步且额外检查归属，恢复期禁止写入 |

关键业务分支已补中文注释。消息恢复只修正寻址，不修改原消息ID、正文、状态与服务器权限校验；退款金额、支付额度和库存仍由原数据库事务控制。
