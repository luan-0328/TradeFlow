# TradeFlow 完整项目升级路线

日期：2026-10-26  
状态：升级建议稿，供后续确定范围与实施使用；不代表目标能力已经实现或验收。  
依据：本地源码、开发资料包 v3.0、当前交付说明及 2026-10-24～25 验证报告。本次仅整理文档，没有重新执行测试、连接服务器、修改业务代码或迁移数据库。

## 1. 当前是不是最小版本

当前适合定义为：**单商家、单仓库、模拟支付范围内的交易履约与售后第一版，业务实现已有深度，完整工程验收尚未完成。**

它不是只有增删改查的骨架，也不是最终完整的多商户平台。可以称为受限范围的 MVP，但不能因此省略范围内的权限、一致性、异常恢复和验收。已有组件测试和历史联调结果，也不能代表最新源码对应的整套系统已经验收。

当前已经属于微服务架构：五个核心业务服务分别拥有数据，通过接口和事件协作，配有网关、服务发现、独立模拟通道及跨服务恢复。多商户是业务范围扩展，不是微服务成立的条件。

### 1.1 已有能力与边界

| 领域 | 已有实现 | 当前主要边界或缺口 |
| --- | --- | --- |
| 用户权限 | 注册登录、短期 JWT、角色、商家成员关系、权限撤销与审计 | 账号安全与会话使用闭环仍需补齐；完整越权矩阵待验收 |
| 商品库存 | 商品/SKU、报价、库存流水、预占释放、退货库存分级处置、展示缓存 | 单商家单仓库；商品图片、检索、SKU 维护体验待完善 |
| 订单履约 | 多 SKU、购买件快照、幂等下单、取消超时、发货收货、原键恢复 | 一次整单发货；无跨商家拆单；模拟物流 |
| 支付退款 | 独立模拟通道、未知结果恢复、关闭屏障、退款双额度与资金流水 | 无真实支付接入、商户结算与提现 |
| 售后 | 未发货退款、金额仅退款、退货退款、逐件权益、证据、验收及库存处置 | 一次验收全部通过或拒收；平台争议处理待设计 |
| 消息对账 | Outbox/Inbox、延期隔离、原 ID 重放、冻结账单及双向差异修复 | 部分绑定缺失风险已复现；完整监听容器与 Broker 故障验收待补 |
| 前端运维 | 用户端、商家/平台控制台、人工待办、指标日志、交付和备份工具 | 最新页面端到端、实际业务灾备、通知送达及容量验收未完成 |

### 1.2 最近已确认的工程缺口

- CI 明确跳过 Java 测试；六个应用启动测试最近报告为错误，源码仍存在早期 SKELETON 断言。
- MQ 部分绑定缺失时，只要另一个目标仍能收到，Broker ACK 与 mandatory 不能发现缺失接收方；原事件仍可被标记 SENT。
- 真实 Nacos 验收受本机隔离条件阻塞；不能将编译或跳过用例算作发现联调通过。
- 六库合成恢复通过，不代表实际业务库、证据文件、在途任务与消息已经完成整套恢复演练。
- 最近服务器部署记录存在低内存下支付持续超时；这是历史结果，本次没有重新核实服务器。
- 本次检查时，本地 feat/bootstrap 分支没有提交，项目文件未跟踪；发布清单版本固定为 0.1.0，缺少源码版本到验收结果的明确绑定。
- 售后人工任务后端最多读取 100 条，统一待办页面的局部分页不能解决来源截断。

依据见 [可靠性实测](integration/2026-10-25-reliability.md)、[加固记录](project-hardening.md)、[交付状态](delivery-status.md)。部分旧文档仍保留历史表数、骨架和直连描述，需统一修订，不能择取有利结果当作最新状态。

## 2. “完整”的目标与方案选择

完整应当有明确终点：业务角色能独立完成工作，异常有处理入口，数据可追溯，版本可交付，故障可恢复，关键结论有证据。它不等于实现所有电商功能。

| 方向 | 覆盖范围 | 取舍 |
| --- | --- | --- |
| A：完整单商家系统 | 在现有业务范围内补齐产品体验、可靠性与交付 | 范围最小，适合单个企业；不能展示多商家隔离和平台结算 |
| B：多商户交易平台（推荐） | 商家入驻和隔离、各自经营、跨商家交易组织、平台治理、模拟结算及工程验收 | 能承接现有商家归属和交易能力；需要逐阶段增加规则与数据模型 |
| C：真实商业运营平台 | 在 B 上接真实支付、渠道分账、真实物流、结算提现及外部经营要求 | 依赖真实商户资质、渠道协议和运营条件，不能仅靠代码宣称完成 |

本文以 **B 为建议目标**。用户已明确希望做完整项目，但尚未最终确定多商户及资金规则；下述目标是建议范围，不是已经批准的实施设计。A 也是成立的完整项目路线。C 属于独立后续目标。

### 2.1 推荐目标的完成定义

1. 买家能完成商品查找、下单、支付、履约查询、退款退货和结果恢复。
2. 多个商家能入驻并独立管理成员、商品、库存、履约、售后和结算查询，无法操作其他商家数据。
3. 平台能审核商家、处置争议、追踪异常和查看审计；受控恢复不能直接篡改业务终态。
4. 跨商家购物能够按明确规则拆分交易，金额、退款和结算具有唯一事实来源。
5. 在约定负载和故障范围内通过测试；有版本化部署、升级、备份和恢复证据。
6. 继续使用独立模拟支付，模拟渠道账与平台业务账可对账；不将模拟余额、结算或出款描述为真实资金能力。

## 3. 业务范围与规则建议

### 3.1 多商户分两步完成

第一步先做到多商家经营、**每个订单只属于一个商家**。购物袋按商家分组，分别结算，不提供跨商家一次支付。这一步先验证隔离、权限和交易归属。

第二步增加跨商家结算入口：一次结算建立交易组，按商家生成子订单。建议初版仍让每个子订单独立支付，界面清楚展示部分完成和剩余待支付；若要求一次付款覆盖多个商家，则单独设计支付分配、关闭、部分退款和结算协议，不能复用现有一个订单一个 payment_no 的假设。

商家停用应阻止新经营操作，但保留历史订单查询、退款义务和平台接管处理通道。入驻状态、账号状态、成员角色及交易权限分别建模，不用一个 ACTIVE 字段承担全部业务。

### 3.2 金额与结算

- 金额继续使用整数分；价格、商品、商家、地址、运费与优惠分配在受理时保存权威快照。
- 优先增加有明确规则的商家运费模板，再考虑商家优惠券；平台券和跨商家优惠后置。
- 运费和优惠进入交易前必须定义逐件分摊、尾差、部分退款、运费退还及并发权益规则。不能只修改订单总额。
- 模拟结算区分支付本金、退款、平台服务费、应付商家、冻结/待结算金额、结算批次及冲正，不把现有支付账直接当商家可提现余额。
- 结算前退款减少待结算金额；结算后退款需要冲正或后续抵扣。余额不足进入明确的欠款/待处理状态，不能抹去退款义务。
- 对账分为渠道支付退款对账、订单业务核对、商家结算对账，分别报告，不能用一种对账代替全部正确性。
- 真实分账、银行卡与提现接入不属于推荐目标的默认范围。

### 3.3 履约、售后和平台治理

- 多商户阶段先保持每商家一个默认仓库、每订单整单发货，避免同时重写仓储和履约模型。
- 商品图文、多 SKU 新增停用、搜索筛选、地址簿、订单检索和消息中心纳入日常使用能力。
- 增加承运商和运单信息、可追溯物流节点；模拟节点与真实渠道返回必须明确区分。
- 平台争议处理记录证据、原因、裁定和后续执行任务；裁定不等于资金成功，不绕过购买件权益和退款额度。
- 分批发货、自动收货、部分退货验收、多仓调拨列为后续扩展，每项均需独立状态机和并发规则。

## 4. 架构演进

保留现有 Java/Spring、MySQL、RabbitMQ、Redis、Nacos 和 Vue 技术栈，不进行全量重写。

| 能力 | 建议归属 | 边界要求 |
| --- | --- | --- |
| 商家入驻、经营状态、商家资料 | 初期作为 user 内独立商家模块；规模扩大后评估独立 merchant 服务 | 账号与角色仍由 user 负责；商家经营状态有独立契约 |
| 商品、库存、默认仓库 | product | 商家及仓库归属从已授权上下文和权威记录获取 |
| 交易组、商家子订单、履约及权益 | order | 商家子订单是履约与售后边界；不得直接访问其他服务库 |
| 支付、退款、通道事实及渠道对账 | payment | 商家 ID 不能成为绕过支付归属和金额校验的依据 |
| 售后、证据及争议流程 | aftersale | 买家、所属商家和平台分别授权；裁定通过受控业务命令执行 |
| 模拟商家结算 | 建议新增 settlement 服务，在结算阶段落地 | 独立库、账本与对账；消费资金事实并幂等记账，不改支付事实 |
| 站内通知 | 先建设明确模块和接口，是否独立服务由实际需求决定 | 通知失败不回滚交易；不承担资金正确性的权威判断 |

### 4.1 多商户隔离必须贯穿全链路

外部 merchant_id 只能作为待校验的业务选择，不能直接作为可信权限。资源查询、写命令、关联 ID、批量接口、统计、导出、文件访问及恢复接口都要校验归属。

同时检查：数据库唯一键与幂等作用域、Redis 缓存键、报价和购买件快照、事件正文、异步任务、审计、对象存储路径及后台检索。商家字段存在不代表隔离已经实现；也不能只在网关校验后信任内部输入。

多商户并不强制每商家一个数据库。推荐继续按服务分库，在服务内通过商家归属约束隔离；真实数据库约束与应用授权共同保证一致性。跨商家关联通常发生在同一服务库内的交易组模型，不引入跨服务 JOIN。

### 4.2 一致性约束继续有效

- 单服务短事务；事务中不进行远程调用。
- 幂等结果、业务效果、审计及必要 Outbox 在本地事务内一致提交。
- 未知支付退款结果保留占用，按原号查询恢复；不因超时换号重做。
- 购买件权益和支付额度分别约束；仅退款不增加库存；退货后只退剩余合法实付。
- 多副本恢复需要租约、版本围栏和最终条件更新，不能只依赖 Redis 锁。
- 事件兼容、消费幂等、乱序与拓扑变化均需要验证。

## 5. 分阶段升级与验收

各阶段都是交付范围，不是已完成声明；不以服务数量、表数或测试数量代替验收。已有验证可复用，但代码或环境变化影响相关行为时必须复验。

### U0：建立可信的当前版本

交付：

- 建立 Git 基线，检查忽略规则和敏感文件；交付包增加源码提交、构建编号、迁移范围及验证结果引用。
- 修复六个应用测试的配置和过期断言，区分单元、边界、真实依赖集成和全应用测试。
- CI 执行必要测试和前端检查；真实依赖测试配置独立任务或受控环境，不能通过默认跳过伪装全绿。
- 核验 MQ 预期交换机、队列和绑定；建立漂移告警和原事件恢复流程。
- 在合适的隔离环境完成真实 Nacos、七服务、监听容器、Broker 重启及原事件恢复验证。
- 核对旧版业务数据升级路径，补真实业务六库、证据、在途任务和消息的隔离恢复演练。
- 修订 README、架构说明和交付状态中的历史口径。

验收：一个明确版本能从空环境启动，完成购买履约、部分补偿后退货、退款竞争及未知结果恢复；升级后的历史订单可继续处理；故障演练资金库存不变量成立；阻塞项逐项有结论。

这里的“门禁”指合并或发布前必须满足的自动检查与验收条件，不要求新增专用平台。备份恢复不是让旧数据覆盖正常运行环境，而是在隔离目标验证恢复和后续任务收敛。

### U1：补齐单商家日常使用

交付：商品图片及安全上传、多 SKU 维护、基础搜索筛选、地址簿、订单售后检索、业务时间线、账号改密与会话管理、关键通知及人工待办后端分页。

验收：通过用户端和管理端完成真实操作；账号切换、令牌过期、撤权、弱网、刷新、跨标签页和未知结果恢复有验证；商品编辑不改变旧订单快照；修改密码后的会话行为明确；大于 100 条人工任务能完整遍历。

### U2：多商户经营与隔离

交付：商家申请/审核/停用、商家资料与成员管理、店铺商品入口、商家工作台、默认仓库归属、购物袋按商家分组并分别下单。移除固定商家在新业务中的隐含假设。

验收：至少两个商家和多个角色贯穿交易全流程；替换他人的商品、SKU、订单、售后、证据和任务 ID 均无法越权；数据库、缓存、事件及重放不串商家；同一成员切换商家不残留旧数据。商家停用后历史退款和待办仍可处置。

### U3：跨商家交易组织与金额规则

交付：交易组和商家子订单、分组结算页面、部分创建/支付/取消恢复；落地第一套运费规则。商家优惠在金额分摊设计明确后加入，不与拆单一次性混改。

验收：一组内部分成功不伪装整体成功；重复提交和恢复不重复建子订单；各子订单独立履约和售后；子订单和购买件金额可逐分核对；支付超时关闭与迟到成功交错可收敛。

本阶段默认每子订单独立支付。若选择一次合并支付，必须先新增支付分配与退款协议设计，并扩大本阶段验收，不能把一笔通道款虚构为多笔独立实收。

### U4：模拟结算与平台治理

交付：独立结算领域、服务费规则快照、结算资格和冻结期、结算批次、商家账单、退款冲正、结算对账；平台争议处理、操作审计检索与通知升级机制。

验收：同一资金事实重复或乱序到达只记账一次；结算前后退款金额均守恒；任务宕机恢复不重复结算；负向调整和异常余额可追溯；商家只能查看自己的账单；平台裁定能形成实际后续任务并跟踪完成。

模拟结算的应收应付、费用和退款冲正应成对核对，不能以改余额替代账本。真实出款、税务与渠道清算另行设计。

### U5：版本发布与运行验收

交付：固定版本镜像、依赖清单、受控环境配置、HTTPS、凭据轮换、接口契约兼容检查、监控通知、容量测试、升级及故障恢复手册。U0 起持续完善这些能力，U5 做整套验收，不在最后才考虑安全与部署。

验收：在目标资源环境测得接口延迟、错误率、吞吐、CPU/内存、数据库连接和 MQ 积压；压测后核对不变量；验证两个应用实例并发恢复及实例变更；完成告警触发到通知送达、备份到隔离恢复的演练并记录实际 RPO/RTO。

性能、可用性和恢复时间目标在测试前根据运行规模确定，不能先填漂亮数字。单机依赖通过验收不等于高可用；仅测试双应用实例也不代表数据库、MQ 和注册中心具备高可用。

## 6. 存量数据与发布策略

1. 逐项识别 merchant_demo、warehouse_main 在代码、SQL、缓存和脚本中的假设；保留历史归属，不全库替换字符串。
2. Flyway 只能追加。新增表和每个字段写中文 COMMENT，业务方法、RPC、事件和恢复任务维护中文业务注释。
3. 根据既有业务事实核实历史归属，再分批回填；无法证明归属的数据进入核对流程，不能猜测填充。
4. 新增唯一约束或非空约束前检查重复及空值；大表变更评估锁和耗时，变更后核对数据及运行账号授权。
5. 内部接口与事件按兼容扩展、切换、收缩分阶段推进；不兼容发布采用明确停写和协调升级流程。
6. 数据结构升级后，旧 JAR 是否可回退必须单独验证。不能假定镜像回退等于数据库回退，也不能无条件恢复备份丢弃新交易。
7. 每批提供版本、迁移清单、影响服务、停写条件、恢复方式及上线后核验。新前端不得连接不兼容旧后端作为新版本验收。

## 7. 质量与验收矩阵

| 层次 | 要证明的内容 | 不能替代什么 |
| --- | --- | --- |
| 单元与边界 | 状态规则、参数、授权分支、错误契约 | 真实事务、网络和数据库约束 |
| MySQL 集成 | 唯一性、并发、回滚、租约围栏、金额库存守恒 | 七服务协作和真实消息监听 |
| MQ/Redis/Nacos 集成 | ACK/NACK、重投、绑定漂移、缓存隔离、实例变化 | 整套用户业务与部署验收 |
| API 端到端 | 真实服务协作、超时和原号恢复、双商家隔离 | 浏览器交互和人工操作体验 |
| 浏览器验收 | 登录、购买、履约、售后、后台处理、会话隔离 | 资金数据库约束和容量结论 |
| 部署与恢复 | 新装、存量升级、回退边界、故障恢复、通知送达 | 未测试负载下的稳定性 |

跨阶段必须保留的场景：抢最后一件、同键异参、撤权与写入竞争、发货与退款竞争、100 元先补偿 20 元再退 80 元、退款未知、成功回调重复/迟到、旧租约执行者、部分 MQ 绑定丢失、商家 A 访问商家 B 数据、结算后退款及数据恢复后任务重启。

每份报告记录源码版本、环境版本、执行命令、原始日志位置、数据核对和未覆盖条件。测试未执行、被跳过、受环境阻塞、失败和通过分别记录。

## 8. 开始实现前需要确定的业务决策

| 决策 | 本文建议 | 影响 |
| --- | --- | --- |
| 最终定位 | 多商户交易平台，模拟资金 | 决定 U2～U4 是否纳入目标 |
| 商家与仓库 | 多商家，每商家先一个默认仓库 | 避免同时引入多仓分配和调拨 |
| 跨商家付款 | 先分商家下单，再交易组与独立子单支付 | 合并支付将扩大关闭、分配、退款及结算设计 |
| 平台服务费 | 单一、可版本化规则；比例与舍入方式待定 | 影响结算金额和退款冲正，不预设费率 |
| 结算资格 | 以完成履约、售后风险和冻结期共同判断，具体期限待定 | 收货并不自动消灭售后退款义务 |
| 运费/优惠 | 先商家运费，后商家优惠；平台券后置 | 影响购买件分摊、尾差与退还规则 |
| 真实渠道 | 本路线继续模拟，外接时单独验收 | 需要实际渠道条件与协议，不能靠模拟证明 |

这些决策应在对应阶段前明确，不必为了开始 U0 一次讨论完全部细节。本文不授权真实支付开通、服务器变更、生产迁移、提交推送或自动上线。

## 9. 建议执行顺序与项目完成标准

推荐顺序：**U0 → U1 → U2 → U3 → U4 → U5**。U0 先消除已知测试与消息可靠性缺口；U1 让现有业务可日常使用；U2 才正式扩大商家范围。工期在每阶段拆解与验证环境确认后估算，本稿不预填完成日期。

每个阶段继续拆成可独立演示和验收的小批次。例如 U2 先交付商家审核与归属，再完成商品库存隔离，再贯穿订单售后，最后做跨商家越权验收，不能只加商家表和页面就标记完成。

当推荐范围内的业务闭环、权限隔离、金额库存不变量、故障恢复、版本部署和使用文档均验收通过，且剩余限制明确记录时，可以称为“完整的多商户模拟交易平台”。没有真实资金接入不妨碍这个范围内完整；但不得据此宣称真实资金运营或生产高可用已完成。

暂不默认引入分库分表、Elasticsearch、Kafka、Seata、Kubernetes、秒杀或跨地域部署。需要新增技术时，先明确现有方案的测量结果、待解决问题和迁移成本。
