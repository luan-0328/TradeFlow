# B10 履约收货资料与下单未知结果恢复

2026-10-24，沿用用户继续开发授权。不新增表，不改已发布迁移；复用订单地址、幂等请求、创建意图和审计表。业务方法和关键SQL已补中文注释。本轮跳过测试，不SSH或提交推送。

## 商家按需查看地址

普通订单列表和详情仍只带安全快照。后台详情中的“按需查看收货资料”调用`GET /api/v1/merchant/orders/{orderNo}/shipping-address`。

应用先在事务外查询最新有效商家身份；本地短事务锁订单，验证所属关系以及`PAID/SHIPPED + CONFIRMED + NONE`，再读地址并追加不含地址明文的审计。同事务提交才返回收货人、电话、地区和详细地址。其他商家统一404；完成、关闭或存在履约锁时不返回资料。地址DTO禁止默认toString输出，响应no-store。

前端资料只保留当前弹窗内存，关闭、切换订单/账号、发货成功或两分钟后清除。查看和发货动作仍由服务端重新核验；两分钟是页面展示期限，不是可以撤回已被操作者看见的信息。不写入浏览器持久存储。

## 下单原键查询与封键

原问题：创建响应丢失后，浏览器只有原幂等键和摘要，刷新会丢失地址正文。若仅依靠原内容重试，用户可能无法恢复；只查不到订单就换键，会与迟到请求形成重复下单。

- `GET /api/v1/orders/requests/by-key`：原键通过Idempotency-Key请求头传递，固定查当前买家PLACE_ORDER。返回`{found,progress}`。普通一致读不阻塞创建，`found=false`只表示当前不可见，不能当作原请求已失败。
- `POST /api/v1/orders/requests/seal`：相同原键和`{reason}`。用户显式选择“查询并阻止未受理的原请求”。和下单竞争同一用户/操作/原键唯一行，最多三个短事务争用重试，无RPC。
- 下单先提交：封键只返回原业务进度，不取消已有订单，不另建订单。需要取消时通过原订单既有取消流程。
- 封键先提交：保存特殊摘要与`CANCELLED/REQUEST_SEALED`创建意图墓碑、幂等拒绝结果和审计；不创建订单、库存预占、支付或任务。迟到下单识别墓碑，返回原取消编号，永远不再启动该键的创建流程。
- 封键或查询超时：保留原键；再次查询或重复封键。不得在没收到权威结果时清理日记或自动生成新键。

购物袋恢复区在刷新后也可发现当前账号原下单日记。查到业务或封键成功后才标记已确认并按原键清理日记，进入原进度或允许核对购物袋重新提交。查询不到继续保留未知态。恢复无需重新提交地址，不使用原幂等键作为URL或外部账号查询参数。

封键墓碑和原幂等记录不设置TTL。将来归档必须一起保留阻止迟到重放的证据，不能只删幂等行。B11已追加支付和售后申请的原键只读查询；其他后台命令仍保留原键重试机制，未实现通用命令恢复中心。
