## 验证中发现并修复

1. 购物袋在旧单订单请求未确认时可能使用新交易组键再次创建。现先等待旧日记读取并恢复/安全封键，未知时阻止新组；恢复过程中等待命令锁后再次检查页面有效性。
2. 含运费金额超限被当作可重试异常。现持久化REJECTED/ORDER_AMOUNT_LIMIT并完成原任务，不建订单或反复重试。
3. 商家停用后，已提交的运费修改原键结果先被经营状态拒绝。现核对最新账号与归属后优先读取原幂等结果，新修改才检查经营状态。
4. 商品图片Mapper直接返回byte[]被MyBatis当作多行数组，实际读取抛argument type mismatch。改为单行Map中的BLOB字节，真实图片读写/删除/可见性测试通过；静态资源测试同步验证单行映射。
5. 业务端口管理路径落入无资源处理返回500。新增独立管理端口过滤器，与指标采样开关分离；实际七应用业务端口拒绝、管理端口readiness通过。
6. 地址簿增加省市区后补齐运行账号region列授权，专用低权限连接实际执行权限检查；保存地址选择可完整填入下单地址。
7. 六个早期SKELETON应用测试改为显式独立fixture启用的真实本库应用测试，并增加结算完整应用测试。普通环境明确跳过，专用套件强制检查报告非空、无跳过，不以禁用生产校验或空Mapper掩盖失败。
8. 新增测试中Mockito的默认空Map与MyBatis未命中返回null不一致，已修正fixture；生产同号冲突校验未放宽。独立MySQL启动工具移除与临时root连接不匹配的skip-name-resolve，失败实例已按本任务Popen归属停止。

## 复现与证据

```powershell
cd D:/cloud/tradeflow
.\mvnw.cmd -B -ntp -fae test
npm.cmd run build
python scripts/verification/upgrade-mysql.py
```

Maven必须串行。MySQL脚本需要本机MySQL8.0 bin（或TRADEFLOW_MYSQL_BIN）及Python cryptography，只创建新UUID目录和随机回环端口。它使用本次临时密钥和凭据、启动本次应用测试JVM，并在结束时停止自己创建的数据库，不接管其他进程或现有数据库。

最终证据：

- `.local/upgrade-maven-final.log`、`.local/upgrade-unit-summary.json`：普通测试完整结果。
- `.local/upgrade-frontend-build.log`：两端类型检查及生产构建。
- `.local/verification/upgrade-mysql-qnt7dn2j/result.json`、`maven.log`：最终43项、34份迁移散列及SQL检查；`owned_process_stopped=true`。
- `.local/verification/upgrade-mysql-jzu6n_qa/`：前一轮41项通过，尚未加入结算完整应用测试，不与最终结果累加。
- 更早失败目录保留用于复核，均记录自建进程停止，不能把失败轮次记作通过。

fixture目录包含临时PEM、数据库数据及原始日志，不属于发布材料；不要公开或打包这些目录。源码迁移定义117张业务表，表数不代表功能完整度或性能。
