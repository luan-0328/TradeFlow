# 本机恢复故障定向验证（2026-10-25）

本轮执行本地定向回归，发现并修复支付恢复器旧租约仍能回写成功资金事实的问题。没有连接远程服务器，没有重启既有业务进程，没有读取或修改 `.local/mysql/data`，没有删除数据库或测试证据。

## 问题与修正

原 `PaymentService.owns` 只比较 RUNNING 和 claim_version；当租约过期但尚未发生接管时，仍能接受迟到的通道响应。原共享 `PaymentMapper.finishTask` 也缺少 owner 和有效租约条件，调用方未检查影响行数。

支付恢复网络返回后的本地事务现使用数据库 `fenceTask`，统一校验 RUNNING、owner、claim_version、有效租约。完成任务的条件更新再次使用数据库时钟校验，影响行数必须为 1，否则抛异常，回滚同事务成功事实、流水、退款本金账户与 Outbox。订单已不可支付时，关闭阶段转换同样使用 `closeOwnedTask` 条件更新，失败回滚关闭意图。

退款恢复原本已通过 `RefundMapper.fence` 校验完整租约。本轮同步接入强化后的共享完成接口，并检查零行回滚，防止本地应用过程跨过租约后提交资金转换。没有调整金额规则、数据库结构或退款契约。

## 实际执行

首次红灯命令：

```powershell
.\mvnw.cmd -B -ntp -pl tradeflow-order,tradeflow-payment -am `
  '-Dtest=OrderRecoveryFaultTest,PaymentRecoveryFaultTest' `
  '-Dsurefire.failIfNoSpecifiedTests=false' test
```

`PaymentRecoveryFaultTest.expiredLeaseCannotApplyLateSuccess` 在旧代码失败：`paymentMapper.fact(...)` 被调用；支付 4 例中 1 例失败。日志保留在 `.local/fault-red.log`。修正后的相同定向测试通过，日志在 `.local/fault-green.log`。

最终验证命令：

```powershell
python scripts/verification/fault-mysql.py
```

脚本仅使用 `D:/mysql-8.0.46-winx64/bin` 的本机原生工具。每次创建全新临时目录，`--no-defaults` 初始化独立 MySQL，仅绑定 127.0.0.1，随机端口，禁用 mysqlx；导入支付服务现有 V1–V4 迁移，再执行指定的 Java 回归。初始化的空口令 root 只用于该临时隔离实例。脚本最后仅关闭本次创建的实例，保留数据和日志，不读取开发库凭据。

最终结果：MySQL **8.0.46**，Maven **BUILD SUCCESS**，共 **8 例、0 失败、0 错误、0 跳过**。

## 验证边界

本次不是 39 项故障全验收：未真实杀停 JVM，未制造 RabbitMQ confirm/ACK 丢失，未运行完整应用或 Nacos 链路，未做远程部署、负载或性能验证。原预占恢复为编排单元测试，未把库存库和订单库组成真实分布式故障链路。

重复支付成功事实测试覆盖统一资金应用器的重复效果抑制；尚未新增“不同 eventId 表达同一退款”的 Inbox、订单权益结算、双额度退款全链路验证，不能称为重复资金事件结算已经全部验收。退款共享完成接口经过编译并接入回滚检查，但退款专属资金应用跨期测试仍待补充。

未设置 `TRADEFLOW_FAULT_MYSQL_URL` 时，真实数据库测试会显式跳过；不能拿普通单元命令的跳过结果宣称数据库验证通过。独立脚本会启动新实例、执行真实数据库测试并保留证据，可反复运行，不接管已有实例。
