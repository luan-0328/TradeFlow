# U1–U4 业务升级说明

日期：2026-10-26。范围由用户指定：先开发日常使用、多商户、跨商家交易和模拟结算治理，全部开发后统一测试，暂不部署。本次没有 SSH、升级现有业务库或重启既有应用。本文描述源码行为，实际验证结果单独记录，不代表生产验收。

## 1. 业务能力

- 用户：改密、撤销全部旧会话、带版本地址簿和默认地址、站内通知及已读；商家入驻申请和审核结果通知。
- 商品：关键词和店铺过滤、追加 SKU、商品图片上传/读取/软删除。图片在商品本库保存，限制体积和像素并重新编码 PNG，公开读取仅限上架商品；草稿图片须商家认证读取。
- 商家：申请、审核、资料和成员维护、经营启停、当前商家选择；平台商家列表和用户库授权审计查询。
- 订单：商家归属和运费快照、多商家交易组、独立子订单、原键查询恢复、订单状态筛选和时间线。
- 售后：按当前商家隔离列表和写操作、人工任务后端分页；买家申请平台介入，平台裁定及原号退款/终止任务。
- 结算：新增独立 `tradeflow-settlement` 服务和数据库，模拟结算账本、批次、账单、费用和冻结期快照、退款冲正和负债抵扣、账本核对。
- 通知：订单状态日志产生持久通知任务，租约围栏、失败退避、原键去重、平台查询和人工恢复。

用户端增加账号与地址、平台介入、分商家交易列表/详情；控制台增加商家管理、运费规则、争议与审计、商家/平台模拟结算。已有商品页接入图片和 SKU 操作，人工待办增加订单通知来源。

## 2. 固定规则

### 商家与权限

商家 ID 格式 `merchant_[a-z0-9_]{1,48}`，历史 `merchant_demo` 保留。多个商家仍采用服务独立数据库，服务内由商家归属字段和最新成员权限隔离；没有为每个商家建立数据库。

`X-Merchant-Id` 只表达工作空间选择，各服务必须核对最新有效成员关系与角色。单归属允许兼容旧客户端；多归属缺少选择则拒绝，不能默认选第一家。切换商家使前端请求和页面代际失效，并隔离商家写命令日记。

每商家独立成员职级：`merchant_member.role` 为 `ADMIN` / `OPERATOR`。A店管理员可以同时是B店操作员，B店管理权限不能由A店或旧全局商家角色获得。权威 `AuthContext.merchantRoles` 返回有效成员职级（包含经营停用商家），capabilities只聚合必要导航；敏感操作必须校验当前商家职级。平台只能经专用平台入口跨商家维护成员。

V7将历史有效成员中仍有有效全局MERCHANT_ADMIN关联者回填ADMIN，其余OPERATOR；此为一次性历史兼容，新增成员缺省OPERATOR，入驻审核通过授本店ADMIN。职级/状态修改、目标会话撤销和审计同事务；所有授权写与账号停用共享授权锚点，禁止降级/禁用每店最后一个有效且可登录ADMIN，也禁止全局停用该账号。先补授另一有效账号ADMIN再移除原管理员；历史已无可用ADMIN的店由平台专用入口补授，商家经营停用不解除管理员保护或历史售后义务。

仓库仍使用 `warehouse_main` 作为每个全局唯一 SKU 的默认逻辑库存位置；商家隔离通过 SKU→商品归属验证。没有在本批增加多仓、调拨或仓库级分单能力。

### 交易组与运费

`POST /api/v1/trade-groups` 输入 `{orders:[PlaceOrder]}`，最多 10 个不同商家，每个子单最多 20 个 SKU。组、子绑定、原下单意图、运费快照、恢复任务在同一本库事务提交。后续沿原库存/支付 Saga 运行；一个子单失败不伪装为整组成功，也不撤销其他已经成立的子单。

`PlaceOrder` 增加 `merchantId` 和 `expectedShippingCents`；旧默认商家零运费请求保留构造器及原摘要恢复兼容。交易组原键查询 `GET /api/v1/trade-groups/requests/by-key`；组列表及详情 `GET /api/v1/trade-groups`、`GET /api/v1/trade-groups/{groupNo}`。原键只放请求头，不保存浏览器明文地址。

每个子单独立支付，不提供一次通道付款覆盖全部商家。当前运费规则为每商家每单固定金额，0～1000000 分；读取 `/api/v1/shipping-quotes?merchantId=...`，商家管理员通过 `PUT /api/v1/merchant/shipping-rule` 携原键和 `{feeCents,version}` 修改。运费变化须重新确认；旧运费请求结果可按原键恢复，即使商家后来停用。

商品原单价不变；运费按 SKU 数值和购买件编号稳定顺序均分，剩余分依次分配。购买件 `paid_amount_cents` 和行实付包含分摊运费，逐件合计严格等于订单含运费金额。当前退款采用本件剩余实付，包含其分摊运费；不实现“商品可退但运费单独不退”的另一套规则。历史订单无运费快照时按零运费处理。商品与运费总额超过既有金额上限时，持久化明确拒绝。

旧版单订单请求仍未知时，购物袋阻止通过新交易组键重建；须先恢复原单或安全封住原未受理请求。

### 平台争议

`POST /api/v1/disputes` 关联本人原售后和申请依据，原证据继续在售后材料查询。买家查看本人争议，平台分页查询全部争议。

裁定 `APPROVE`/`REJECT` 仅适用于原售后仍待审核：通过后未发货/仅退款交原退款任务，退货仍等待真实退货验收；拒绝交原终止授权任务。`UPHOLD` 保持现有处理。裁定和原售后状态、任务、审计同事务提交，不直接写退款成功，不改变申请金额，不逆转已经执行或终止的授权。已拒绝后的重新申请须走现有合法权益流程，本批不提供任意强制退款。

### 模拟结算

应用默认端口 8087、管理端口 18087。默认费率 0bps、冻结期 7 天，分别配置 `TRADEFLOW_SETTLEMENT_FEE_BPS`、`TRADEFLOW_SETTLEMENT_FREEZE_DAYS`，导入支付时保存规则快照。订单完成收货、冻结期届满且没有活动售后才具备结算资格。

支付和退款成功事实来自 payment 只读资金账 API；原事实号幂等，冲突拒绝。结算后退款追加冲正和商家负债，后续批次优先抵扣负债；不抹去退款义务。没有真实出款、钱包提现、银行卡或渠道分账。

资格 RPC 与结算库之间存在跨库并发窗口，已成功退款通过后续事实冲正收敛。本批不声称存在不可撤销的真实出款屏障。资金自增 ID 不等于提交顺序，扫描在尾部归零重扫以补晚提交空洞；容量优化需要后续提交水位或冻结账单协议，不能直接省略重扫。

## 3. 数据迁移与运行

| 服务 | 新迁移 | 新表 |
| --- | --- | --- |
| user | V6、V7 | merchant、merchant_application、user_address、user_notification |
| product | V6 | product_image |
| order | V8、V9 | merchant_shipping_rule、order_charge_snapshot、trade_group、trade_group_child、shipping_rule_command、order_notification_task |
| aftersale | V5 | platform_dispute |
| settlement | V1 | 独立结算 8 表，详见模块 README |

订单 V8 调整旧行金额 CHECK，使其允许商品原价之外的分摊运费。旧迁移保持不变；新表字段均要求中文 COMMENT。既有运行账号授权脚本同步追加最小表/列权限，资金事实、结算账本及不可变快照不授予任意 UPDATE/DELETE。

本地准备脚本支持结算第八个 JVM；新增 `TRADEFLOW_INTERNAL_SETTLEMENT_TOKEN` 仅分配给 user/order/payment/settlement 等必要调用方，不继承管理员或其他服务数据库密码。只修改准备脚本，不代表本次执行过业务库迁移或启动过现有环境。

升级涉及支付意图新增商家字段、下单请求结构、行实付语义及内部服务凭据，应停写后协调升级，不让旧服务处理新协议。旧版本不理解含运费权益，不能简单回退旧 JAR 继续处理新交易。部署 Compose 及生产发布模板不作为本批已完成或已验收交付，部署留待另行安排。
